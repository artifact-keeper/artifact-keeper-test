# Per-Format Push/Pull Coverage Audit

Status: 2026-04-25, branch `feat/format-coverage-audit-and-gapfill` (issue #48).

Tracks Phase 3 of [Hardening Core](https://github.com/orgs/artifact-keeper/projects/2).

## Problem

The release-gate format matrix has uneven coverage. Some scripts exercise the
real native client (`npm publish`, `pip install`), some only hit the
format-native HTTP endpoint with `curl`, and some only hit the management API
at `/api/v1/repositories/{key}/artifacts/...`.

The third category does not catch protocol regressions visible to the actual
user-facing client. The community reported that the docker format was broken
between releases; no gate caught it because the docker batch in CI runs
`test-oci.sh`, which defaults to a curl-based simulation of the OCI v2 protocol
(`USE_DOCKER=false` unless `FORCE_DOCKER_TESTS=true` is set, which never is in
the release-gate workflow).

This doc inventories what each format suite actually does, names the gap, and
records what was added in this PR.

## Definitions

For this audit, a test counts as **native-client** only if it shells out to the
real client binary (`mvn`, `npm`, `pip`, `twine`, `docker`, `apt-get`, etc.).

A test counts as **format-native HTTP** if it uses `curl` against the
format-specific endpoint (`/maven/...`, `/npm/...`, `/v2/...`, `/debian/...`,
`/generic/...`, `/pypi/...`). This catches protocol-level regressions but does
not catch client-compatibility issues (auth header dialects, content-type
negotiation, redirect handling, tarball field names that real clients are
strict about).

A test counts as **management-API only** if it hits
`/api/v1/repositories/{key}/artifacts/...`. The management API is shared
infrastructure and a passing test there proves nothing about the format
handler.

## What this PR adds

Four new scripts under `tests/formats/`. All four are wired into the
release-gate workflow's format matrix in `.github/workflows/release-gate.yml`
and the reusable `format-tests.yml`:

1. `test-maven-native-client.sh`
   - Runs `mvn deploy:deploy-file` to push a tiny synthetic JAR against
     `/maven/{key}/`.
   - Runs `mvn dependency:get` to pull that JAR back into a clean local
     repo and verifies the JAR exists.
   - `require_cmd mvn`. Skips the entire suite if the runner has no `mvn`.

2. `test-pypi-native-client.sh`
   - Builds a real sdist tarball.
   - Runs `twine upload --repository-url ${BASE_URL}/pypi/{key}/` to push.
   - Runs `pip install --index-url ${BASE_URL}/pypi/{key}/simple/` to pull
     into an isolated `--target` directory and verifies the module imports.
   - `require_cmd python3`. Skips early if `twine` or `pip` is not on the
     PATH (installs `twine` via `pip install --user` when possible).

3. `test-docker-native-client.sh`
   - Builds a tiny `FROM busybox:1.36.1` image (pinned digest, no `:latest`).
   - Runs `docker login`, `docker push`, `docker pull` against the in-cluster
     registry hostname.
   - Skips cleanly if any of: `docker` CLI absent, `docker info` fails (no
     daemon), or the registry hostname does not resolve from the runner.
   - This is the test that would have caught the regression Firjen reported.

4. `test-generic-native-client.sh`
   - PUT/GET against `/generic/{key}/{path}` with `format_auth_header` (Basic).
   - Verifies SHA256 round-trip, deeply nested paths, and 404 on missing
     paths via the format-native endpoint, not the management API.

## Debian native-client gap (blocked)

`apt-get install` from a custom apt repository requires:

1. A signed `Release.gpg` and `InRelease` file. Backend produces these only
   when a GPG signing key is configured, which is not the case for the
   release-gate test deploy. We would need to provision a key, register the
   public part with apt's `signed-by`, and re-deploy.
2. Either trusting the unsigned repo with `[trusted=yes]` in the sources
   list and tolerating the warning, or installing the public key into the
   runner's `/etc/apt/keyrings/`.
3. `apt-get update` followed by `apt-get install -y` running with root,
   which the ARC runner pods do not have by default (they run as the
   `runner` UID).

These are tractable but each one is its own change. Adding them in this PR
would balloon the diff and would only flake until all three are in place.
The blocker is therefore filed as a follow-up, with the existing
`test-debian.sh` and `test-debian-conformance.sh` continuing to provide
format-HTTP coverage in the meantime.

When the follow-up lands the test should:

- Configure `apt` against `${BASE_URL}/debian/{key}/` with `[trusted=yes]`.
- Run `apt-get update` and confirm the `Packages` index parses.
- Run `apt-get install --download-only ${PKG_NAME}` and verify the .deb
  appears in `/var/cache/apt/archives/`.

The `--download-only` form avoids the dpkg install step, which is what
makes the test cleanly idempotent on a runner pod.

## Wiring

Every new script is added to:

- `.github/workflows/release-gate.yml`, in the format-tests matrix, in the
  appropriate batch (`jvm`, `python`, `containers`, `generic-protocol`).
- `.github/workflows/format-tests.yml`, in the parallel matrix used by the
  reusable workflow callers.

The `scripts/run-suite.sh` orchestrator auto-discovers `tests/<suite>/test-*.sh`
via `find`, so local runs and `--filter` invocations pick up the new scripts
without further changes.
